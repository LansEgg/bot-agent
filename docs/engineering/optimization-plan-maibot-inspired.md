# 基于 MaiBot 启发的人格化演进、MCP 与插件生态架构优化方案

> 状态：**规划与设计阶段**。
> 参考基线：开源智能体项目 [MaiBot (MaiSaka)](https://github.com/Mai-with-u/MaiBot)、[MaiBot 文档中心](https://docs.mai-mai.org/) 与 [Model Context Protocol (MCP) 规范](https://modelcontextprotocol.io)。
> 实施原则：**小步快跑、阶段隔离、每步必审（Review Gate）、验证闭环**。
> **核心铁律**：严禁一口气全量重构！每个阶段和原子任务必须遵循 **“修改局部代码 -> 严格 Code Review -> 运行探针/测试验证 -> 人类确认签入 -> 进入下一子任务”** 的开发纪律。

---

## 1. 背景与对标分析 (Why & What)

### 1.1 MaiBot 的核心哲学与技术精髓
[Mai-with-u/MaiBot](https://github.com/Mai-with-u/MaiBot) 是活跃在多聊天平台（QQ、NapCat、官方通道等）的人格化 LLM 智能体。其核心理念与技术特征为：
1. **“最像人而不是最好”（More lifelike, not merely better）**：
   - 彻底摒弃传统 AI 助手的“AI 味”（拒绝长篇大论、机械分点和过度格式化）；
   - 强调口语化、随性、真实的人类社交表达。
2. **读懂气氛与动态发言时机（Read the room）**：
   - 不再局限于被动的“一问一答”或固定的阈值轮询；
   - 能够感知群聊动态氛围，具备独立的情绪冲动、发言欲望与适时沉默机制。
3. **分层长期记忆与认知图谱（A-Memorix 架构）**：
   - 将记忆沉淀为事件片段（Episodes）、实体画像（Profiles）、证据链（Evidence）与强化/遗忘生命周期；
   - 针对群友画像具备“证据推导 + 人工覆盖”的双层模型。
4. **语言自进化与亚文化融入**：
   - 自动捕获群聊中的“黑话/俚语”（Jargon）并理解其语境；
   - 表达方式（Expression）与风格聚类模仿，越聊越像群友。
5. **社交多模态与 Prompt 治理**：
   - 表情包（Emoji）的生命周期管理（上传、审核、封禁、场景推荐）；
   - Prompt 模板多语言版本化与可覆盖系统。
6. **成熟的插件体系与 MCP 集成架构**：
   - **Host / Runner 进程隔离**：主进程与插件运行进程解耦，插件故障不拖垮主核心；
   - **MCP 客户端统一底座**：支持 `stdio` / `streamable_http` / `sse` 三大传输模式，提供 `stdio_filter` 过滤非标准横幅日志污染，工具与插件工具平权注册进 `ToolRegistry`；
   - **强类型 Manifest 规范**：清晰界定工具、命令、拦截钩子（Hooks）与受控权限代理。

### 1.2 当前项目 (`BotAgent`) 的现状与演进空间
- **现有优势**：
  - 高效轻量的 .NET 8 / C# 常驻进程，内存占用低（~50MB vs Python 百兆级），启动极速；
  - 具备平台中立的多通道架构（`IPlatformAdapter`：QQ 私域、QQ 官方、飞书、本地通道）及统一的平台实例策略矩阵；
  - 完善的脱敏安全机制（`AGENTS.md` 隐私红线、自动化审计脚本、合成测试替身）与嵌入式 Web 管理面板；
  - 拥有严谨统一的工具目录（`ToolDirectory`、`ToolSpec`、`IToolExecutor`、`ApprovalFlow` 审批流）及基础 MCP 治理抽象；
  - 已支持去动作化叙述过滤（`StripActionNarrations`）与基础的 `Desire`（发言欲望）/ `Threshold` 机制。
- **现存差距**：
  - **记忆结构偏扁平**：现有的 `BotConversation` 与 `MemberProfile` 主要基于轻量键值与简单摘要，缺乏关系图谱、记忆事件片段生命周期（衰减、强化、证据链）与时空关联；
  - **交互缺乏“群聊生命感”**：虽然有欲望计数器，但仍偏向机械衰减，缺少群聊情绪热度判定、话题插嘴切入点计算以及主动发表情包的拟真节奏；
  - **语言风格缺乏自适应能力**：尚无对群内流行梗、缩写、新词（Jargon）的自动识别与语境沉淀；
  - **Prompt 与人设治理硬编码**：人设提示词主要通过环境变量与配置项整体拼装，缺乏模板切片管理与版本回滚机制；
  - **插件与 MCP 尚未形成合力**：现有的 MCP 工具与内部业务逻辑割裂，缺少统一插件包规范（Manifest）、事件拦截 Hook（Before/After Chat）、动态生命周期热插拔以及统一的 WebUI 扩展卡片。

### 2.1 模块一：群聊氛围感知与动态发言意愿 (Atmosphere & Desire Engine)
- **氛围指标**：
  - 聊天流频次热度（Messages/Min）、情绪基调（活跃、低落、争论、平静）；
  - 话题相关度（群友是否在讨论 Bot 熟悉的话题或提到 Bot 名字的谐音/别名）。
- **非线性欲望计算**：
  - 引入疲劳阻尼（连续多次发言后，发言意愿大幅衰减，进入冷却，防止在群聊中刷屏讨人嫌）；
  - 话题破冰与适时沉默（当检测到群友正在两人深度对私密话题沟通时，主动抑制欲望）。

### 2.2 模块二：分层长期记忆与证据链画像 (Memory & Profile Engine)
参考 MaiBot 的 A-Memorix 架构，将记忆自底向上划分为三层：
1. **Raw Log / Messages**：近实时消息流（受现有脱敏隔离保护，不直接外漏）；
2. **Episodes（记忆片段）**：异步提炼的有价值会话单元（包含发生时间、涉及实体、关键事实摘要与情感极性）；
3. **Profiles & Evidence（画像与证据链）**：
   - 记录用户属性（喜好、特征、习惯），每条属性关联到具体的 Episode 作为证据（Evidence）；
   - 提供 WebUI 上的“人工覆盖”（Override）能力，人工设定优先级高于 AI 推断。

### 2.3 模块三：圈子黑话与表达方式自进化 (Jargon & Expression Engine)
- **黑话识别管道（Jargon Pipeline）**：
  - 检测群聊中高频出现的未知缩写、网络流行词或专有代称；
  - 结合上下文推断语义，并标记为 `pending` 状态；
  - 管理面板支持对捕获的黑话进行审核（`confirmed` / `discarded` / `manual`）；
  - 将通过审核的黑话适度注入 System Prompt，使 Bot 在对应群聊中自然使用该圈子的特定表达。

### 2.4 模块四：表情包生命周期与多模态表达 (Emoji & Expression)
- 建立表情包资产目录，管理表情包文件的 Hash、语义标签（开心、无语、疑惑、嘲讽等）、使用频次及封禁状态；
- 当情感匹配度达到阈值时，随文本一同触发或单独发送表情包，极大增强类人质感。

### 2.5 模块五：MCP 与原生插件生态融合架构 (MCP & Plugin Ecosystem)
结合 MaiBot 的 Manifest 组件机制与成熟的 MCP 规范，在本项目中构建**“双轮驱动、统一治理”的能力生态架构**：

#### 1. 双轮驱动架构 (Dual-Track Architecture)
- **轨道 A：原生 .NET 插件 (Native AssemblyLoadContext Plugins)**
  - 采用 .NET 8 可卸载式 `AssemblyLoadContext`（或可选的轻量子进程隔离）加载第三方 `.dll` 扩展包；
  - 具备原生极致性能与低延迟，直通内部消息事件流。
- **轨道 B：MCP 开放协议生态 (Model Context Protocol Ecosystem)**
  - 将外部 MCP Server 直接当作“跨语言无代码插件包”；
  - 完美复用 Python、Node.js、Go 等外部庞大生态，开发者无需编写任何 C# 代码即可接入（如文件系统、GitHub、浏览器自动化、外部数据库等）。

#### 2. 标准化 Manifest 契约 (`_manifest.json`)
每一个插件（无论是 Native 还是 MCP 包装包）均须提供清晰的元数据清单：
```json
{
  "manifest_version": 2,
  "id": "bot.plugin.weather",
  "name": "实时天气查询",
  "version": "1.0.0",
  "author": "Developer",
  "entry_type": "native_assembly", // 或 "mcp_server"
  "capabilities": ["tools.register", "hooks.observe"],
  "mcp_config": {
    "transport": "stdio",
    "command": "uvx",
    "args": ["mcp-server-weather"]
  },
  "permissions": {
    "network_outbound": true,
    "file_access": false
  }
}
```

#### 3. 插件核心组件扩展点 (Component Extensibility)
- **`ToolComponent`**：向 LLM 声明受控能力，统一注册进既有 `ToolDirectory`；
- **`CommandComponent`**：前台斜杠命令注册（如 `/dice`、`/status`）；
- **`HookHandler`**：关键生命周期拦截与观测（`BeforeChat` 消息重写、`AfterChat` 行为审计、`BeforeToolCall` 权限截断）；
- **`HomeCardComponent`**：向 WebUI 面板注入自定义状态监控卡片。

#### 4. MCP Host 稳健性与防污染机制 (Robust MCP Host Engine)
参考 MaiBot 的优秀实践：
- **`stdio_filter` 容错管道**：对 stdio 子进程的 stdout 进行实时过滤，丢弃非 JSON-RPC 的启动 Banner、框架日志或空行，防止协议流解析崩溃；
- **保留名称冲突两层防御**：
  - *第一层（内核保留字）*：`reply`、`silent`、`ask`、`stop` 等核心保留字严禁被插件或 MCP 工具占用，冲突时拒绝注册并报警；
  - *第二层（跨 Server 冲突）*：按注册优先级去重，优先保留高优先级或先装配的服务工具；
- **高级回调支持 (Host Callbacks)**：
  - 支持 MCP `client.sampling`（反向调用大模型）、`logging`（统一日志汇聚）、`roots`（受控目录暴露），默认开启 Fail-Closed 保护。

#### 5. 统一安全治理网关 (Unified Governance Plane)
所有 Native 插件工具和 MCP 外部工具，必须无一例外地接入本项目的**治理基础设施**：
- **三层治理策略**：`Tool` > `Server` > `Connection` 优先级裁决；
- **审批流接轨 (`ApprovalFlow`)**：高风险能力（如外部执行、文件修改、敏感数据读取）必须触发一次性待批单，严禁越权静默执行；
- **脱敏红线防护**：插件上下文（`PluginContext`）严禁向外提供未脱敏的群聊原始报文或真实用户隐私。

## 3. 核心实施纪律：阶段性审查门禁 (Step-by-Step Review Gate)

> ⚠️ **【首要铁律】：改完一部分代码，必须完成针对性 Review 与自动化验证，确认无误后再进行下一步！**

为了坚决防止大面积修改导致的架构腐化、抽象破坏、内存泄漏或引入未测 Bug，实施过程中强制执行 **Review Gate（审查门禁）机制**。特别是插件系统与 MCP 接入涉及动态装载、子进程管理与权限跨越，存在极高的安全与稳定性风险，**绝对严禁越过门禁一次性推进多个任务**！

### 3.1 研发四步循环 (The 4-Step Discipline Loop)

每一个原子任务（无论修改规模大小）必须严格遵照以下四步闭环推进：

```
   ┌────────────────────────────────────────────────────────┐
   │ 1. Minimal Diff Coding (遵循分层架构，仅做最小必要修改) │
   └───────────────────────────┬────────────────────────────┘
                               ▼
   ┌────────────────────────────────────────────────────────┐
   │ 2. Self Review & Verification (自我审查与探针自动化回归) │
   └───────────────────────────┬────────────────────────────┘
                               ▼
   ┌────────────────────────────────────────────────────────┐
   │ 3. Explicit Review Gate Check (5 级门禁清单核验)        │
   └───────────────────────────┬────────────────────────────┘
                               ▼
   ┌────────────────────────────────────────────────────────┐
   │ 4. Git Checkpoint & Next Step (确认达标并存档，再启下步)│
   └────────────────────────────────────────────────────────┘
```

### 3.2 审查门禁核心检查清单 (Review Gate Checklist)

在宣布任何一部分代码完成、并准备着手下一步之前，**必须逐项审查并通过以下 5 个门禁核验**：

| 门禁项 | 审查内容 | 判定标准 |
| :--- | :--- | :--- |
| **G1: 架构与职责合规性** | 是否严格遵循 Domain -> Services -> Adapters 分层？新逻辑是否复用了公共基础设施？是否破坏了现有抽象？插件机制是否遵守 Domain 零 IO 规则？ | 严禁跨层直接调用；严禁浅模块膨胀；通过 `ArchitectureProbe` 架构护栏 |
| **G2: 隐私与脱敏红线** | 是否涉及群聊真实昵称、发言、敏感凭据或真实 IP？插件上下文是否能够非法窥探未脱敏的聊天日志？是否遵循了 `AGENTS.md` 脱敏规范？ | 严禁日志输出或持久化未脱敏内容；测试数据必须使用合成替身；插件上下文绝对禁止暴露原始用户私密数据 |
| **G3: 自动化测试与探针** | 核心逻辑是否有单测？是否运行了前端与集成探针？是否有任何破坏既有行为的 Regression？ | `dotnet test`、`FrontendProbe`、`SafetyProbe` 必须全部 100% 绿色通过 |
| **G4: 最小化 Diff 审查** | `git diff` 是否只包含本步骤必需的改动？是否存在误删、格式混乱、临时调试代码或无关依赖？ | Diff 必须清晰紧凑，杜绝一切无关污染 |
| **G5: 步骤确认与交接** | 向用户明确报告本步骤审查结论（改动了哪些文件、通过了哪些测试、存在何种边界考量），获得确认后方可解锁下一阶段。 | 未经 Review 并确认，绝对不启动下一步骤的代码编写 |

## 4. 分阶段实施里程碑 (Phased Milestones)

每个里程碑被拆分为若干独立可控的原子任务。**前一个任务未通过 Review 门禁前，严禁开始下一个任务。**

### Milestone 1: 拟人对话节奏与群聊氛围感知
- **任务 1.1**：定义领域模型 `ChatAtmosphere` 与情绪热度计算逻辑。
  - *Review 重点*：时间窗口滑动算法性能，内存无泄漏。
  - *验证*：单测验证消息频次与情感热度推导。
- **任务 1.2**：重构 `DesireEngine`，增加疲劳阻尼与连续对话冷却机制。
  - *Review 重点*：现有群聊私域与官方通道的兼容性，不能导致现有主动发言逻辑死锁。
  - *验证*：运行 `SafetyProbe` 与回复节奏模拟测试。
- **任务 1.3**：对接 WebUI 管理面板，在「回复节奏」卡片新增相关可视化参数。
  - *Review 重点*：移动端响应式布局与数值保存持久化。
  - *验证*：运行 `FrontendProbe` 确保无前端截断与控制台异常。

### Milestone 2: 圈子黑话（Jargon）学习与自动进化
- **任务 2.1**：在存储层设计 `JargonEntry` 实体与 SQLite Schema 迁移。
  - *Review 重点*：Schema 兼容旧数据库，支持租户隔离（群维度隔离）。
  - *验证*：数据库初始化与读写测试。
- **任务 2.2**：编写异步 Jargon 识别提取服务与提炼过滤算法。
  - *Review 重点*：后台任务并发与 LLM 消耗预算防护，防止高频群聊耗尽 Token。
  - *验证*：利用 MockOpenAi 合成对话流进行提取测试。
- **任务 2.3**：实现 WebUI 黑话管理界面（审核、手动添加、禁用、导入导出）。
  - *Review 重点*：输入框 XSS 安全防护与脱敏显示。
  - *验证*：前端探针 + API 契约测试。

### Milestone 3: 分层长期记忆（Episodes & Profile Evidence）
- **任务 3.1**：构建 `EpisodeStore` 记忆切片仓储，支持时序与语义标签存储。
  - *Review 重点*：低内存开销，SQLite 索引设计合理性。
  - *验证*：批量插入与范围查询性能基准测试。
